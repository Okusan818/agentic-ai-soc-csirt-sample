# この事例の設計判断

A社に当てはめるときに行った判断を記録する。汎用の一式のADR([docs/decisions/](../../docs/decisions/README.md))と同じく、
背景・決定・理由・検討した代替案・変更するときの影響範囲を書く。

## D-01: 封じ込めエージェントを、モデルを使わない実行関数にする

| 項目 | 内容 |
|---|---|
| 背景 | [AI-001](../../02-agentic-ai/02-01-architecture.md) は封じ込めエージェントを「AIエージェント」としている。A社では措置の実行関数のIDが悪用されたときの影響を最小にしたい |
| 決定 | 措置の候補は統合エージェントがRunbookの手順から選び、実行の可否はオーケストレーターが規則で決め、実行はモデルを使わない関数が決められたAPIで行う |
| 理由 | 措置の実行の段階にモデルを置く利点がない。モデルがツールを持たない構成にすると、プロンプトインジェクションで措置が実行される経路がなくなる([AI-005](../../02-agentic-ai/02-05-ai-specific-threats.md)) |
| 代替案 | モデルに措置のツールを持たせ、オーケストレーターが呼び出しを検査する案。検査の漏れが措置に直結するため採らなかった |
| 影響範囲 | [EXA-005](05-agent-implementation.md) 第2章・第3章 |

## D-02: Defender for Business の自動修復を、製品の防御機能として受け入れる

| 項目 | 内容 |
|---|---|
| 背景 | Defender for Business の自動調査と修復は自動化のレベルが固定され、オーケストレーターの権限レベルの判定を経ずに実行される |
| 決定 | 製品の防御機能として受け入れ、実行された修復を判断ログに「製品の自動修復」として記録し、日次のレビューの対象に含める |
| 理由 | 修復の多くはファイルの検疫・プロセスの停止で可逆的である。自動化を設定できる上位のライセンス(Defender for Endpoint Plan 2)は、160名規模では費用の増加に見合わない |
| 代替案 | Defender for Endpoint Plan 2 に切り替え、自動化のレベルを端末のグループごとに設定する案。保護資産のサーバーで自動修復が業務に影響した場合に再検討する |
| 影響範囲 | [EXA-006](06-actions-and-protected-assets.md) 第5章、[EXA-005](05-agent-implementation.md) 第6章 |

## D-03: 夜間・休日のLv2を、MDR事業者の契約範囲の措置に限る

| 項目 | 内容 |
|---|---|
| 背景 | [GOV-005](../../01-governance/01-05-operating-hours.md) は夜間・休日のLv2の事後確認をTier2の当番に求める。A社には30分以内に確認できる社内の当番がいない |
| 決定 | 夜間・休日は、MDR事業者が事後に確認できる措置(端末の隔離)だけをLv2とし、それ以外のLv2の措置はLv3として扱う(`PA-02`) |
| 理由 | 事後確認ができない措置を自動実行すると、Lv2の前提(人間が短時間で確認し、問題があれば元に戻す)が成り立たない。Lv3への引き上げはAI-002の規則を厳しくする方向であり、規則に反しない |
| 代替案 | 社内の当番の応答目標を30分にする案(2名の当番では負担が大きく、続かない)。夜間のLv2を全面的にLv3にする案(端末の隔離まで遅れ、ランサムウェアの初動に間に合わない) |
| 影響範囲 | [EXA-003](03-organization-and-operations.md) 第3章、[EXA-006](06-actions-and-protected-assets.md) 第2章、[EXA-004](04-parameters.md) |

## D-04: Kill-switchを発動できる人を広げる

| 項目 | 内容 |
|---|---|
| 背景 | [AI-004](../../02-agentic-ai/02-04-audit-and-kill-switch.md) は発動できる人をSOCマネージャー以上としている。A社では該当する人が1名で、不在のときに発動できない |
| 決定 | 情報システム主担当・副担当・情報セキュリティ責任者の誰でも発動できる。解除は情報セキュリティ責任者が行う |
| 理由 | 発動は自動実行を止める(安全側の)操作であり、発動が遅れるほうが危険である。解除は安全側から外れる操作のため、責任者に限る |
| 代替案 | MDR事業者にも発動を認める案。外部の事業者に社内の統制の操作を任せないため採らなかった(MDR事業者は発動を依頼できる) |
| 影響範囲 | [EXA-003](03-organization-and-operations.md) 第5章、[EXA-005](05-agent-implementation.md) 第7章 |

## D-05: FortiGateでの遮断は、外部脅威フィード(遮断リストのファイル)を介して行う

| 項目 | 内容 |
|---|---|
| 背景 | URL・ドメイン・IPアドレスの遮断をFortiGateにも反映したい。FortiGateは保護資産(セキュリティ基盤)である |
| 決定 | 措置の実行関数は遮断リストのファイルに追記するだけとし、FortiGateが定期的にそのファイルを取得して遮断する |
| 理由 | 実行関数にFortiGateの管理者権限を与えずに済む。誤って追記した場合も、リストから外せば元に戻る |
| 代替案 | FortiGateのREST APIでアドレスオブジェクトを直接追加する案。APIの管理者権限で他の設定も変更できてしまうため採らなかった |
| 影響範囲 | [EXA-006](06-actions-and-protected-assets.md) 第2章 |

## D-06: SIEMにMicrosoft Sentinelを置く

| 項目 | 内容 |
|---|---|
| 背景 | Microsoft 365とDefenderのアラートだけなら、Defenderポータルでも確認できる |
| 決定 | Sentinelを置き、FortiGate・ドメインコントローラ・Azure Backupのログも集める |
| 理由 | 証拠収集サービスの取得元を1つにし、調査範囲をコードで強制するため([AI-006](../../02-agentic-ai/02-06-evidence-grounded-investigation.md))。ランサムウェアの事案(EXA-012)では、侵入経路(VPN)とバックアップの状態がMicrosoft 365の外にある |
| 代替案 | MDR事業者のSIEMを使う案。証拠パッケージと判断ログを自社で保持できず、[AI-003](../../02-agentic-ai/02-03-decision-logging.md) の要件を満たしにくいため採らなかった |
| 影響範囲 | [EXA-002](02-product-configuration.md)、[EXA-007](07-evidence-sources.md) |

## D-07: 制御系セグメントに専用の監視製品を置かない(現時点)

| 項目 | 内容 |
|---|---|
| 背景 | 制御系の機器にはDefenderを導入できず、制御系の内部は監視できない |
| 決定 | 当面はFortiGateのセグメント間の通信ログだけで監視し、制御系の内部を「未確認」として常にケースに表示する |
| 理由 | 制御系専用の監視製品は、A社の規模では費用と運用の負担が大きい。「未確認」を明示する仕組みがあれば、監視していないことを前提に判断できる(EXA-012) |
| 代替案 | パッシブ型のネットワーク監視製品を制御系に置く案。取引先からの要請の水準が上がった場合、または設備の更新時に再検討する |
| 影響範囲 | [EXA-006](06-actions-and-protected-assets.md) 第3章、[EXA-007](07-evidence-sources.md) 第1章 |
