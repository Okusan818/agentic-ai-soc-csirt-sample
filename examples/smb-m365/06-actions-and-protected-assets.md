# 措置の実装と保護資産

[AI-002](../../02-agentic-ai/02-02-authority-levels.md) の規則(権限レベルの判定、保護資産、AIが実行しない操作、承認者)を、A社の製品と資産に当てはめる。
規則自体は変えない。権限レベルは、[EXA-004](04-parameters.md) の値(`P-09` = 1、`P-10` = 3)で判定する。

## 1. 措置と実行方法

各Runbookの対応手順にある措置を、A社で実行する方法と、AIに実行させるかどうかに分ける。

| 措置 | Runbook | 実行方法 | AIの実行 | 権限レベル |
|---|---|---|---|---|
| 端末のネットワーク隔離 | [SOC-003](../../03-soc-runbooks/03-03-malware-detection.md)、[SOC-004](../../03-soc-runbooks/03-04-ransomware-precursor.md) | Defender for Endpoint API(端末の隔離) | 実行する | 対象数による(保護資産はLv3) |
| 悪性ハッシュの遮断 | SOC-003 | Defender のカスタムインジケーター(ファイルハッシュ) | 実行する | Lv1(IoC 1件=1対象) |
| 悪性URL・ドメイン・IPアドレスの遮断 | [SOC-002](../../03-soc-runbooks/03-02-phishing.md)、SOC-003 | Defender のカスタムインジケーター、Exchange Online のテナントの許可/禁止リスト、FortiGateの外部脅威フィード(第2章) | 実行する | Lv1(許可リストに該当する場合はLv3) |
| メールの隔離 | SOC-002 | Exchange Online・Defender for Office 365 の管理者による修復 | 実行する(要確認) | Lv1(IoC 1件=1対象) |
| 不審なセッションの無効化 | [SOC-001](../../03-soc-runbooks/03-01-anomalous-login.md)、SOC-002 | Microsoft Graph(サインインセッションの無効化) | 実行する | 対象数による(管理者アカウントはLv3) |
| パスワード変更の強制 | SOC-002 | オンプレミスのActive Directory(同期しているアカウントのため) | 実行しない | Lv3(人間が実行) |
| 承認記録のない権限付与の取り消し | [SOC-006](../../03-soc-runbooks/03-06-privilege-escalation.md) | Entra ID・Active Directoryの管理画面 | 実行しない | Lv3(人間が実行) |
| 外部共有の非公開化 | [SOC-007](../../03-soc-runbooks/03-07-cloud-misconfiguration.md) | SharePoint・OneDriveの共有設定 | 実行しない | Lv3(人間が実行) |
| 外部共有機能の一時的な制限 | [SOC-005](../../03-soc-runbooks/03-05-insider-threat.md) | SharePointの管理画面 | 実行しない | Lv3(人間が実行) |
| バックアップへの経路の遮断、サーバーの停止、セグメントの遮断 | SOC-004 | Azure Backup、FortiGateのポリシー、サーバーの操作 | 実行しない | Lv3(人間が実行) |

### AIに実行させない措置の理由

- **パスワード変更の強制**: A社のアカウントはオンプレミスのActive Directoryから同期しており、パスワードの変更はActive Directory側で行う。
  ドメインコントローラは保護資産であり、措置の実行関数にActive Directoryの操作権限を与えない。
- **権限の取り消し・共有設定の変更**: 実行に必要なAPIの権限(ディレクトリの書き込み、全サイトの書き込み)が広すぎ、
  実行関数のIDが悪用されたときの影響が大きい([AI-005](../../02-agentic-ai/02-05-ai-specific-threats.md))。AIはケースと手順の下書きまでを作り、人間が実行する。

いずれも、汎用の一式の「対象数による」措置を、A社の判断で「Lv3」に引き上げたものである(引き下げではないため、AI-002の規則に反しない)。

> **要確認:** Defender for Office 365 Plan 1 で使えるメールの修復の方法(管理者による削除・移動の機能の範囲とAPI)を導入時に確認すること。
> 使えない場合は、メールの隔離を「Lv3(人間が実行)」とし、自動削除機能(ZAP)の動作を判断ログに記録する。

## 2. 実行関数の権限

措置の実行関数(`mi-containment`、[EXA-005](05-agent-implementation.md) 第3章)には、第1章で「実行する」とした措置の権限だけを与える。

| 措置 | 付与する権限 | 範囲の限定 |
|---|---|---|
| 端末の隔離 | Defender for Endpoint API の端末の隔離・隔離の解除 | 保護資産の端末は、実行関数がタグで判別して拒否する(第3章)。API側で拒否できない分をコードで補う |
| インジケーターの登録 | Defender for Endpoint API のインジケーターの登録 | 登録は「遮断」と「有効期限あり(既定30日)」に限る |
| テナントの許可/禁止リスト | Exchange Online のテナントの許可/禁止リストへの禁止の登録 | 許可の登録はしない |
| FortiGateの外部脅威フィード | 遮断リストのファイル(Blob Storage)への追記 | FortiGateの管理者権限は与えない。FortiGateがHTTPSでリストを定期的に取得する |
| セッションの無効化 | Microsoft Graph のサインインセッションの無効化 | 対象を「一般ユーザー」の管理単位に限る。管理者・サービスアカウントは管理単位に含めない |

FortiGateの設定を変更する権限をAIに与えず、遮断リストのファイルを介して遮断する。リストのURLは社外から参照できないようにし、
リストへの追記はすべて判断ログに記録する([EXA-031](31-design-decisions.md) D-05)。

### 夜間・休日のLv2(`PA-02`)

夜間・休日は、Lv2と判定された措置のうち、MDR事業者の契約範囲の措置(端末の隔離)だけをLv2として実行し、MDR事業者が事後に確認する。
それ以外のLv2の措置(複数のアカウントのセッションの無効化など)は、夜間・休日はLv3として社内のオンコールに承認を求める([EXA-003](03-organization-and-operations.md) 第3章)。

## 3. 保護資産

[AI-002](../../02-agentic-ai/02-02-authority-levels.md) 第3章の区分に、A社の資産を当てはめる。保護資産リストはSharePointリストで管理し、
Sentinelのウォッチリスト `ProtectedAssets` に同期する。端末はDefenderのデバイスタグ `Protected` でも識別する。

| 区分 | A社の資産 |
|---|---|
| 認証・基盤 | ドメインコントローラ(Entra Connectを同居)、Entra IDの管理者アカウント(グローバル管理者、緊急用アカウント)、ドメイン管理者アカウント |
| 基幹業務 | 生産管理システムのサーバー |
| 制御系 | 制御系セグメントのすべての機器(NC工作機械、PLC、設備監視用のPC)、設備担当の保守端末 |
| セキュリティ基盤 | FortiGate、Sentinelのワークスペース、ログ収集用の仮想マシン、Agentic AI基盤、Azure Backupのコンテナー |
| 業務上必須の通信先 | Microsoft 365・Azure、取引先とのEDI(受発注)の接続先、生産管理システムの保守事業者の接続先 |

- 工場の共用PC(情報系セグメント)は保護資産としない。ただし生産に使うため、`P-10` を3に抑えて同時に多数を隔離しないようにする。
- 制御系セグメントの機器にはDefenderを導入していない(機器の保守条件による)。制御系のログはFortiGateの通信ログだけであり、
  制御系の機器の端末のイベントは常に「未確認(ログソース未接続)」になる([EXA-007](07-evidence-sources.md))。
- 保護資産リストの棚卸しは、半期ごとと設備の追加・更新のつどに行う(`P-24`)。

> **カスタマイズ:** 制御系の監視を強化する場合は、制御系専用の監視製品(パッシブ型のネットワーク監視)の導入を検討し、
> [EXA-007](07-evidence-sources.md) の取得元に加えること。

## 4. 承認者

| 措置の範囲 | 承認者(Lv3) | Lv2の事後確認者 |
|---|---|---|
| 情報系の端末・アカウント・IoC | 情報システム主担当(主担当が起案した場合は副担当) | 有人時間帯は主担当・副担当、夜間・休日はMDR事業者(端末の隔離のみ) |
| 保護資産(制御系を除く)・業務の停止を伴う措置 | 情報セキュリティ責任者 | ―(保護資産はLv2にならない) |
| 制御系への措置、工場の生産に影響する措置 | 情報セキュリティ責任者(工場長と協議) | ― |
| Kill-switch有効中 | 上記と同じ | ―(Lv2は発生しない) |

## 5. 製品の自動修復とMDR事業者の措置

AIの措置のほかに、次の2つの経路で措置が実行される。いずれも [AI-002](../../02-agentic-ai/02-02-authority-levels.md) のオーケストレーターの判定を経ないため、扱いを定める。

| 経路 | 内容 | 扱い |
|---|---|---|
| 製品の自動修復 | Defender for Business の自動調査と修復(ファイルの検疫、プロセスの停止など)。自動化のレベルは製品側で固定され、変更できない | 製品の防御機能として受け入れる。実行された修復は判断ログに「製品の自動修復」として記録し、日次のレビューの対象に含める |
| MDR事業者の措置 | [EXA-003](03-organization-and-operations.md) 第4章の契約範囲の措置 | 判断ログに「外部の事業者による措置」として記録し、継続か解除かを人間が判断する(`P-12`) |

- オーケストレーターは、措置の前に対象の状態(隔離済みか、インジケーターが登録済みか)を確認し、同じ措置を重ねて実行しない。
  MDR事業者がすでに隔離した端末は、AIの措置の対象数に数えない。
- Kill-switchは、AIの措置だけを止める。製品の自動修復とMDR事業者の措置は止まらない。AIの誤判定の連鎖を止める目的には十分だが、
  製品の誤検知による業務への影響を止めるには、Defenderの除外設定とMDR事業者への連絡を別に行う。

> **要確認:** 自動修復が保護資産のサーバーで実行される場合の動作(検疫の対象、サービスの停止の有無)を、導入時に検証環境で確認すること。
