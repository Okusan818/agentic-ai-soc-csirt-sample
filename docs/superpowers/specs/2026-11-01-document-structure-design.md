# 設計書: 全体文書体系・リポジトリ構成

## 1. 背景・目的

本プロジェクトは、Agentic AIを活用したSOC(Security Operation Center)・CSIRT(Computer Security Incident
Response Team)の運用を想定した、設計書・運用手順書・記録フォーマット一式をサンプルとして作成し、GitHub上で
公開することを目的とする。

本文書は、その一式を構成する6つのサブプロジェクトすべてが従う土台(リポジトリ構成・命名規則・文書書式・
公開条件)を定める。

本一式全体は、**NIST CSF 2.0 (Govern/Identify/Protect/Detect/Respond/Recover の6機能)を前提とする
評価・整理の枠組み**として構築する。各サブプロジェクトの文書は、自身がどのCSF機能に主として対応するかを
明示し(第2章の対応表を参照)、最終的にはサブプロジェクト6(記録フォーマット・KPI・CSF成熟度評価)で
全体の機能水準をNIST CSF 2.0に基づき評価できるようにする。

### 1.1 前提条件

- 本一式は**サンプル**であり、利用者が自組織の利用サービス・体制に応じて修正して使うことを前提とする。
- 特定のセキュリティ製品・SIEM製品の固有名詞には依存しない(製品名を書く箇所は `<SIEM製品>` のような
  プレースホルダーで記述する)。
- 以下を既に導入済みであることを前提とする:
  - Agentic AIを用いたSOC運用基盤
  - SIEM、および各セキュリティ製品のログをSIEMへ連携する仕組み
- 想定運用規模: 従業員約1万人、構成会社100社のグループ企業。コーポレート(親会社)の指示のもと、
  グループ専任のシステム子会社がセキュリティ運用を担う構成。オンプレミスとクラウドの双方に資産を持つ。
- SOC・CSIRTの機能範囲の定義は、Exabeam社の解説記事
  (SOCとCSIRT:6つの主な違いと両方が必要な組織とは?)に基づく。
- SOC・CSIRTが果たす機能水準の評価、および本一式全体の構造化の前提として NIST CSF 2.0
  (Govern/Identify/Protect/Detect/Respond/Recover) を用いる。
- 文書本文は Markdown、図は Mermaid で作成する。

## 2. サブプロジェクト構成

本文書化作業は、以下6つのサブプロジェクトに分割して順に設計・文書化する。

| # | サブプロジェクト | 主なNIST CSF 2.0対応 | 配置先 |
|---|---|---|---|
| 1 | 全体文書体系・リポジトリ構成(本文書) | - | `00-overview/` |
| 2 | 組織・ガバナンス設計 | Govern | `01-governance/` |
| 3 | Agentic AI運用設計 | Govern / Protect | `02-agentic-ai/` |
| 4 | SOC運用手順書群 | Detect | `03-soc-runbooks/` |
| 5 | CSIRT運用手順書群 | Respond / Recover | `04-csirt-playbooks/` |
| 6 | 記録フォーマット・KPI・CSF成熟度評価 | 全機能 | `05-records-kpi/` |

## 3. リポジトリ構成

```
/
├── README.md                 # 全体像・読む順序・前提条件(サンプル利用上の注意)
├── LICENSE                    # CC BY 4.0
├── 00-overview/                # 本プロジェクトの前提・用語集・NIST CSF 2.0対応表の索引
├── 01-governance/               # 組織・ガバナンス設計
├── 02-agentic-ai/                # Agentic AI運用設計
├── 03-soc-runbooks/              # SOC運用手順書
├── 04-csirt-playbooks/            # CSIRTプレイブック
├── 05-records-kpi/               # 記録フォーマット・KPI・CSF成熟度評価
└── assets/diagrams/              # 再利用頻度の高いMermaid図のソースのみを切り出して配置
```

## 4. 命名規則

- ディレクトリ: `NN-slug/`(`NN`はサブプロジェクト番号の2桁、`slug`は英語ケバブケース)
- ファイル: `NN-mm-document-name.md`(`NN`はディレクトリ番号、`mm`はディレクトリ内の連番2桁)
  - 例: `01-01-organization-structure.md`
- 文書ID: ディレクトリの分類コード(`GOV` / `AI` / `SOC` / `CSIRT` / `REC` など)+ 連番3桁
  - 例: `GOV-001`
- 文書間で相互参照する場合は、ファイルパスではなく文書IDで引用する
  (ファイル移動・リネームに強くするため)。

## 5. 文書共通ヘッダー仕様

すべてのMarkdown文書は、本文冒頭に以下の引用ブロックを置く。

```markdown
> **文書ID**: GOV-001
> **バージョン**: 0.1.0
> **改訂日**: 2026-11-01
```

- バージョンはSemVerに準拠した3桁表記(`0.1.0`)とし、内容に実質的な変更があった場合に更新する。
- 改訂日はISO 8601形式(`YYYY-MM-DD`)。

## 6. Mermaid図の扱い

- 原則として、図は文書内に直接 ```mermaid``` コードブロックとして埋め込む。
- 複数文書から参照される図(例: 全体アーキテクチャ図)のみ `assets/diagrams/*.mmd` に切り出し、
  各文書からは画像化せずMermaidソースへの参照コメントで案内する。

## 7. 言語・公開方針

- 文書は日本語のみで作成する。
- ライセンスは **CC BY 4.0** とし、ルートに `LICENSE` ファイルを配置する。
- `README.md` には、本一式が特定ベンダーに依存しないサンプルであり、利用者が自組織の構成に合わせて
  修正利用する前提であることを明記する。

## 8. 本サブプロジェクトのスコープ外

- 各サブプロジェクトの内容(組織設計の詳細、Agentic AIの権限設計、手順書の内容など)は、本文書の
  スコープ外とし、各サブプロジェクトの設計書で個別に定める。
- リポジトリの可視性(公開/非公開の切替タイミング)や公開先アカウントの選定は、利用者側の運用判断と
  する。
